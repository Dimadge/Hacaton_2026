# BE-08 — Принятие оффера, подписание и демо-выдача

## Что добавлено

Этот патч рассчитан на **уже установленный BE-07**, существующую БД `alfa` и текущий `feature/backend-fastapi`. Не удаляйте том PostgreSQL (`docker compose down -v` запрещён, если данные нужны). SQL-миграций нет.

Весь путь проходит только с ролью `CLIENT` и только для заявки его компании. Денег и юридически значимой подписи нет: обе операции **демонстрационные**. JWT-токен не публикуйте на скриншотах.

| HTTP | URL | Тело | Условие |
|---|---|---|---|
| POST | `/api/v1/applications/{application_id}/accept` | `{"version": 4, "offer_id":"UUID"}` | `OFFERED`, оффер из актуального решения по этой заявке |
| POST | `/api/v1/applications/{application_id}/sign` | `{"version": 5}` | `ACCEPTED`, имитация подписания |
| POST | `/api/v1/applications/{application_id}/disburse` | `{"version": 6}` | `SIGNED`, имитация выдачи |
| POST | `/api/v1/applications/{application_id}/cancel` | `{"version": 4}` | `OFFERED`, отказ клиента |

`version` всегда берите из актуального `GET /api/v1/applications/{application_id}` или из предыдущего ответа перехода — цифры в примерах условные. Все ответные суммы и платежи должны оставаться Decimal/строками. Пример ответа успешного действия:

```json
{"id":"UUID_ЗАЯВКИ","status":"ACCEPTED","version":5,
 "accepted_offer_id":"UUID_ПРЕДЛОЖЕНИЯ","simulated":true}
```

### Установка

1. Сохраните незакоммиченные изменения, проверьте `git status`.
2. Из корня проекта выполните:

```sh
unzip -o ~/Downloads/alfa_navigator_BE08_patch.zip -d .
docker compose up -d --build
docker compose exec api python -m pytest -q
```

Ожидается **83 passed** для текущего кода и зависимостей. Тесты локально используют fake DB, полный сценарий обязательно проверяется отдельно с PostgreSQL.

3. Откройте `http://localhost:8000/docs` и убедитесь, что есть четыре новых POST метода. Войти можно через `POST /api/v1/auth/login` демо-клиентом и затем `Authorize` (без слова Bearer, если Swagger ожидает Bearer Token).

### Что проверить СЕЙЧАС без DS

- Текущая заявка `0cda98d2-6d1d-4d8e-b1da-a42df03b0780` уже находится в `NEED_INFO`. Вызов `/accept` с ней должен вернуть **409**, а не выдать кредит. Для этого используйте токен **её собственного клиента**.
- `GET /api/v1/applications/{application_id}/offers` возвращает пустой набор для заявок без оффера.
- Попытки сделать `/sign` или `/disburse` для `DRAFT`, `CHECKING` или `NEED_INFO` должны вернуть **409**.
- В `GET /api/v1/applications/{application_id}/events` не должно появиться дополнительных событий из-за неуспешных запросов.

### Полный E2E после интеграции DS

1. Создать заявку клиентом, отправить и выполнить ФНС/БКИ.
2. DS возвращает скоринг и допустимый лимит платежа; Decision Engine создаёт решение и реальные строки `alfa.credit_offers` через серверные правила, а заявка получает `OFFERED`.
3. `GET /offers` возвращает ID допустимого предложения, который выбирает клиент.
4. `/accept` с ID выбранного оффера и `version` -> `ACCEPTED`.
5. `/sign` с актуальной версией -> `SIGNED`.
6. `/disburse` с актуальной версией -> `DISBURSED`. Это исключительно демонстрация.
7. `GET /events` содержит все переходы, а `GET /offers` отмечает выбранный вариант `accepted: true`.

**Защита**: все операции используют PostgreSQL `FOR UPDATE`, версию заявки и единый transaction scope. SQL-триггер `application_audit` сам пишет event log; приложение не вставляет события вручную. Неверный переход = HTTP 409. Чужая заявка = 404. Сотрудник банка не может вызвать клиентские методы = 403.

### Важные ограничения

- **Нельзя честно продемонстрировать успешное ACCEPTED -> SIGNED -> DISBURSED**, пока DS не передал скоринг и BE не научился безопасно создавать `OFFERED` на основании результата. Мы не засеваем фиктивные одобрения и не обходим защиту БД.
- Ветка `NEED_INFO -> CHECKING` (после уточнения анкеты) ещё требует отдельной проверки / доработки ресабмита.
- Не выполнены live интеграционные E2E тесты с PostgreSQL, CI и frontend сборка.
