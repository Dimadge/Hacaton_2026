# Демо-сценарий для экспертов: Альфа.Навигатор

**Цель:** за 10–20 минут самостоятельно пройти весь цифровой путь с клиентской и банковской ролями. Это **синтетический MVP**, реальных банковских операций нет. Условия кредита, mock-проверки и оценка залога — демо.

## Подготовка (однократно на чистом компьютере)

1. Запустить Docker по [README](../README.md#быстрый-запуск).
2. Запустить `docker compose run --rm seed`.
3. Открыть http://localhost:5173. Клиентам назначен пароль `DEMO_CLIENT_PASSWORD` из `.env`, банкиру — `DEMO_BANK_PASSWORD`.
4. Для **полного локального сценария подписи** в `.env` установить `DEMO_SIGNING_CODE_VISIBLE=true`, затем `docker compose up -d --force-recreate api`. Использовать только изолированный демо-стенд. При `false` шаг выдачи OTP возвращает 503 — это намеренная защитная настройка.
5. Для чистого показа начинайте **новую заявку**, а не уже окончательно отклонённую.

## Сценарий А. Положительный кредитный путь

### Клиент: заявка

1. Войти `client_good@example.test` (значение `DEMO_CLIENT_PASSWORD`).
2. Открыть **Новая заявка** → продукт **Инвестиционный**.
3. Пример **тестовых** сведений (можно менять, но от них зависит риск):

   | Поле | Пример |
   | --- | --- |
   | Цель | Покупка оборудования |
   | Сумма | 1 000 000 ₽ |
   | Срок | 36 месяцев |
   | Среднемесячная выручка | 1 500 000 ₽ |
   | Операционные расходы | 900 000 ₽ |
   | Текущие платежи по долгам | 50 000 ₽ |
   | Возраст бизнеса | 36 месяцев |
   | Резерв | 800 000 ₽ |
   | Подтверждение сведений | Да |

4. Если нужно продемонстрировать залог, **перед отправкой** добавьте к черновику объект: недвижимость; описание «Коммерческое помещение, 80 м²»; собственник — компания; заявленная стоимость **2 500 000 ₽**. Эти данные вымышленные.
5. Отправить. Ожидается `DRAFT → CHECKING`; версии и события сохранены. Проверки FNS/BKI должны происходить по mock-профилю данного клиента.

### Банкир: проверка и решение

6. Выйти и войти как `bank@example.test` (значение `DEMO_BANK_PASSWORD`).
7. В очереди открыть заявку и проверить статус, FNS/BKI, а также финансовые параметры.
8. При наличии залога нажать **Оценить залог**, указать оценочную стоимость **2 000 000 ₽**, отсутствие обременений и текстовый комментарий; нажать **Принять залог**. Ожидается статус `ACCEPTED` у объекта залога.
9. В блоке **Кредитные ограничения** сравнить: лимит максимального ежемесячного платежа по DS и **1 400 000 ₽** — учебный лимит по залогу (`2 000 000 × 70%`). Залоговый лимит и платежный лимит одновременно обязательны для применимого сценария.
10. Нажать **Рассчитать скоринг**, затем **Проверка**. Результат зависит от исходных данных: `OFFERED`, `UNDER_REVIEW` или `REJECTED`. При ручном рассмотрении банк может предложить допустимые сумму/срок или запросить данные. **Не обходите правила**: если выбранные показатели не позволяют кредит, используйте корректный тестовый набор или покажите ветку отказа.

### Клиент: выбор, подписание, выдача

11. Выйти и снова войти под клиентом. Открыть заявку в `OFFERED`, выбрать предложение. Ожидается `ACCEPTED`.
12. На **локальном стенде с включённым деморежимом** нажать «Получить код», ввести показанный шестизначный код и подтвердить договор; статус `SIGNED`. Код действует **5 минут**; неудачные попытки ограничены.
13. Нажать **Получить средства**; итоговый статус `DISBURSED` означает только **симуляцию**, без движения денег.
14. Проверить историю заявки в интерфейсе или через `GET /api/v1/applications/{id}/events`.

> На **публичном** сервере с `DEMO_SIGNING_CODE_VISIBLE=false` интерфейс подписания не выдаст OTP. Это не ошибка сети; шаг блокируется умышленно, пока нет безопасного способа доставки. Жюри может пройти до `ACCEPTED`, а шаг OTP проверить локально.

## Сценарий B. Ручное рассмотрение / уточнение

1. Войти как `client_manual@example.test`, создать новую заявку с полной анкетой, отправить.
2. У этого профиля синтетический `BKI: minor_delay`.
3. Войти банкирским аккаунтом, открыть заявку и нажать **Проверка**; при необходимости расчитать скоринг. Ожидается необходимость рассмотрения человеком (`UNDER_REVIEW`), а не автоматическое положительное решение.
4. Банкир выбирает запрос дополнительной информации (`REQUEST_INFO`), заполняет причину и комментарий. Клиент получает `NEED_INFO`, редактирует анкету/добавляет пояснение и повторно отправляет; статус возвращается к `CHECKING`.

## Сценарий C. Обоснованный отказ

1. Войти `client_reject@example.test`, создать **новую** заявку и отправить.
2. Mock БКИ содержит `critical`.
3. Банкир проводит проверку: ожидается негативное решение с `CREDIT_HISTORY_CRITICAL` и конечным статусом `REJECTED`.
4. Не допускается изменение конечной заявки задним числом; создайте новую для другого сценария.

## Сценарий D. Лимиты и защита ролей

- С заявленным залогом **2 млн ₽ по оценке** вручную попробовать предложение **1,5 млн ₽**. Должна сработать проверка `COLLATERAL_LIMIT`; сумма в пределах 1,4 млн ₽ только **проходит залоговую часть** и всё равно проверяется по DS.
- Клиентский JWT не должен давать доступа к `/api/v1/bank/applications` (`403`).
- Второй клиент не должен читать чужую заявку (`404`/запрет на уровне API).
- Неверный/истёкший OTP не подписывает договор, а повторная подпись невозможна.

## Фиксация результатов

Рекомендуемые материалы для экспертной проверки: 5–7 **обезличенных** скриншотов (регистрация, создание заявки, банковская карточка, DS + залог, решение, история статусов, успешные тесты). **Не публикуйте скриншоты с токенами Bearer, паролями или персональными данными.**
